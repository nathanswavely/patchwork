A third party read the code and sent findings. This release is what came of
them: two privacy fixes on the public quilt endpoint, one authorization gap,
one governance write that could leave git and the database disagreeing, and
the consistency work that made those bugs possible in the first place.

Nine pull requests since v0.29.0, one decision record, no migrations. No
config key, volume or endpoint changes.

## The quilt no longer says what a private patch is near

`GET /api/v1/nodes/tree` is public and carries the pairwise scores the quilt
lays tiles out by. The patch list was filtered to public, active patches. The
shared-member and shared-follower scores were not, and the links were never
checked against the list before they went out. So a private, removed or
suspended patch that shared a person with a public one had its id in the
public response, along with how many people it shared with which public
patches. The id is a UUIDv7, so it also dates the patch. Nothing was drawn:
the quilt ignores a link whose end it has no tile for. The data was in the
JSON, for anyone who fetched it.

Every link is now checked against the returned patch set before it is
serialized, and the member and follower queries carry the same visibility
filters the event queries already had.

**Hidden memberships no longer count toward placement.** A person who hid a
membership still contributed 3 to that patch's score with every patch they
were also in, and because the scores are plain counts with no floor, a pair's
score moving by exactly 3 when one person joined was that person, on a small
patch. Affinity now treats a hidden membership as absent, on the member,
follower and shared-event terms alike.

The member count is deliberately not changed. A count says how big a patch
is and the quilt sizes tiles by it. A pairwise score says a specific overlap
exists, which with hidden rows in it is the membership by another route. See
`docs/adr/2026-09-18-a-hidden-membership-does-not-place.md`, which amends
docs/adr/021.

**What you will notice:** after upgrading, a tile whose patch has hidden
members may sit somewhere else on the quilt. That is the fix working.

## A reaction takes the standing a comment takes

Posting a comment on a proposal asked whether the caller had a role on the
patch and, for a follower, whether the patch lets followers into its
proposals. Adding or removing a reaction asked only whether the comment
existed. A signed-in stranger could react on any comment on any patch,
including one that had closed its proposals to followers.

Both reaction routes now run the same two checks a comment runs and refuse
with the same bodies. A follower on a patch that excludes followers from
proposals can no longer react there either; that follows from the patch's
own rule rather than a new one.

This was found by the new route-table test, described below, not by the
review.

## A merge cannot outrun its record

Applying an amendment merges a git branch and then writes the sha and the
`in_effect` state to the proposal row. Those writes were separate
statements, and their errors were discarded. A locked database at the wrong
moment amended the charter in git, mirrored it into the governance hub, and
left the proposal saying it was still open, with nothing in the log.

The sha and the state now land in one transaction on every path that
applies a proposal: the direct change, the ratified nomination, the
auto-applied amendment and the admin's apply. If a write fails after the
merge has already happened, which SQLite cannot undo, the failure is written
to the audit log as `proposal.apply_incomplete` with the proposal id, the
step and the merge sha. If you have ever seen a charter change with no
matching proposal state, this is the line to search for from now on.

Two smaller records were wrong in the same way. `seat.filled` was audited
even when the seat write had failed. Five audit entries (claim requested,
verification domain set, owner assigned, and both tag-suggestion decisions)
were storing the caller's IP as the payload and the payload as the IP, the
same swap v0.29.0 fixed in three other places. Entries already written stay
as they are.

## Also in this release

- **Audit payloads are marshalled, not assembled.** Ninety call sites built
  their JSON with `Sprintf`. Every value in them was validated first, so
  none was a bug, and each was one free-text field away from becoming one.
  They go through `json.Marshal` now, with a test that refuses a new
  hand-built literal. Key names and value types are unchanged.
- **One timestamp layout for new rows.** Two formats were being written to
  the same columns, and a string comparison misordered them inside a
  second. New writes use the millisecond form everywhere; reads accept
  both, and existing rows are left alone. Values that leave the instance
  in a documented format (the attestation protocol, feeds, the CSV upload
  contract) are unchanged.
- **Every mutating route is asked who it lets in.** A test walks the route
  table and sends each non-GET route two requests, anonymous and from a
  signed-in user with no role on the patch, and fails unless the answer is
  a refusal or the route is on a list with a reason beside it. Route
  registration moved out of `main` into `cmd/patchwork/routes.go` to make
  that possible; the routes themselves are the same.
- **CI runs staticcheck, errcheck and the race detector.** Staticcheck found
  fifteen things, all fixed, including a dead first pass in the comments
  handler that built a result and threw it away. Errcheck is gated on a
  committed baseline so it flags new discards only. The race detector runs
  on the packages with shared state on every pull request and on the whole
  tree nightly; it found nothing.
- **The e2e suite waits on conditions, not clocks.** Seventy fixed sleeps
  are gone.

## Upgrading

```sh
docker compose pull patchwork && docker compose up -d
```

No migrations run. Rolling back to v0.29.0 is clean: the older image reads
every row this one writes, including the timestamps, and the only thing it
gives back is the two leaks.
