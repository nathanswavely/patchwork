**Read the first two sections before you upgrade.** This release changes what
strangers can see of every patch already on your quilt, and it does so on
purpose. The rest is ordinary good news: trust that fits one patch, an admin
Overview that lists what is waiting on you, and visitor counts that watch
nobody.

Fourteen pull requests since v0.28.0, seven decision records, four migrations.

## Members and governance start closed, and existing patches are closed too

Patch admins on the reference instance believed their member list was not
public. It was. Their proposals, the discussion under them, and every
commenter's name were world-readable too, with no control over any of it.
Every setting involved worked as documented; a patch was simply born
enumerable, and the switch to close it could only be found afterwards by an
admin who already suspected something.

Three defaults flip in this release, and **all three are applied to the
patches you already have**, not only to new ones:

- **Public member list** is retracted to `nobody` on every patch. A patch
  that deliberately chose `everyone` is overridden with the rest, because the
  audit log does not record which field an edit touched and the two cannot
  be told apart. Reopening it is one dropdown at Patch Settings, Members,
  under "Public member list". The member count stays public; the quilt sizes
  tiles by it.
- **Public governance record** is new, and every patch starts at `nobody`.
  It covers proposals and their bodies, proposal comments, and both kinds of
  attestation. Same page, under "Public governance record". Proposal lists
  still answer with the setting stated, so a client can tell "nothing decided
  yet" from "withheld".
- **Followers no longer read members-only charters.** The
  `follower_permissions.charters` grant shipped on since migration 012, and
  since following needs nobody's approval it made the private shelf one click
  away from any signed-in stranger, on an invite-only patch included.
  Published charters are unaffected.

Patchwork tells each patch's admins about the third change itself, on first
boot after the upgrade, because it is editing their rules file and the record
should say so. **It does not notify anyone about the first two.** Tell your
patch admins before you upgrade that their member lists and proposals will go
private, and where the two switches are. See
`docs/adr/2026-09-18-the-default-should-match-the-assumption.md` and
docs/adr/116.

Two related defects fixed on the way: the governance overview named every
admin with no gate at all, including admins who had hidden their membership,
and `GET /api/v1/proposals/{id}/comments` was mounted with no auth wrapper.
Both now follow the record setting and the member's own visibility switch.

## A follower is not a quieter member

Found on the live build: click Follow on any patch, open Patch Settings,
find your own row with an editable role dropdown, and set it to admin. The
member listing returned every active row including followers, and the role
update validated the word but never the transition. Promotion out of
follower is now refused and points at invitations; `/members` lists members,
and `?role=follower` asks for followers. See docs/adr/117.

**The git charter repositories carried members' email addresses.** The
smart-HTTP transport hands over the whole bare repo, and four call sites were
writing the commit author as the member's real email rather than the
`username@patchwork.local` form docs/adr/110 describes. That is the one field
the personal export withholds. Clone access is now limited to admins and
members of the patch, and every commit author goes through one function. A
repository somebody already cloned keeps what it has; Patchwork cannot recall
it. If your instance federates or you have handed out clone URLs, this is the
paragraph to weigh.

An instance admin can still self-promote on any patch. That is the
docs/adr/115 reach question, deliberately still open.

## A hidden member's vote no longer federates

A ballot broadcast a `gv:Vote` carrying the voter's actor to every remote
follower, with no gate. Only a member can vote, so the activity was a
membership assertion, and it went out for members who had hidden their
membership on this very instance. A hidden member's vote is now withheld from
federation outright rather than anonymised, and a proposal or charter still
federates but no longer names its author when the author is hidden. Copies
already delivered stay delivered. See
`docs/adr/2026-09-18-a-vote-is-a-membership-said-out-loud.md`.

## Trust has a scope, and a suggestion carries its calendar

A person told to suggest a listing for an organisation he does not run read
past the one muted sentence, created the patch, and became its admin. The
path he was meant to take was worse than it looked: a suggestion queued for
the instance admin, then every event queued again for the same admin, and the
suggester was never told the outcome.

- **Creating a patch opens on a question**: is this your patch to run? "I run
  this patch" opens the form; "Someone else runs it" goes to the suggest
  form. Claim setup skips it.
- **The trusted-contributor grant now has a scope**, the whole quilt or one
  patch. Every gate about one patch reads the scoped grant: posting and
  editing events, CSV upload, the link handshake, and event sources, which
  reverses docs/adr/031's exclusion. A claim clears the grant.
- **A suggestion may carry a feed URL.** It is probed on submit and parked on
  the listing; the review card shows the feed and its upcoming count, and
  approving attaches it and grants the suggester trust on that patch, each
  with an uncheckable line. The suggester is told either way, with the
  admin's note on a decline.
- **Trust requests.** Asked from the event form on an unclaimed patch, with a
  scope picker. Answered from Admin, Users at whatever scope the admin judges
  right, wider or narrower. One open per person, a 30-day cooldown after a
  decline.

See `docs/adr/2026-09-18-trust-has-a-scope-and-a-suggestion-carries-its-calendar.md`.
Three audit calls in the suggestion path had metadata and IP swapped since
they were written; fixed.

## Admin Overview replaces the stats page

The admin panel's landing page was growth counts and links to tabs one click
away. It is now the **Overview**: one line per decision queue with the count
and the age of the oldest item, a "needs attention" list that follows
custody (claimed patches with no active admin, failing aggregators, failing
feeds on unclaimed patches, failed federated deliveries), and plain
statements such as mail being off or the caller holding no passkey.

`GET /api/v1/admin/stats` is removed and `GET /api/v1/admin/overview` takes
its place. Nothing in the product read the old route; a script of yours might
have.

## Visitor counts, off by default

A server-side gauge, no script in the page, no cookie banner. Turned on at
Admin, Usage, it counts page loads per route pattern per UTC day and distinct
visitors per day from a salted hash the server forgets at midnight and on
restart. Only daily totals are stored, pruned after 13 months, and they stay
behind in a seamrip. See
`docs/adr/2026-09-18-counting-visitors-without-watching-anyone.md`.

The shipped privacy policy now says which way the switch is set, corrects
its claim that the web server keeps request logs (the shipped Caddyfile
writes none), and names the map tile servers. **If you overrode the privacy
policy** at Administration, Legal, your text is untouched and the new
paragraph does not appear; reconcile it by hand, especially before turning
counting on. The Caddyfile carries a commented access-log recipe with address
masking and 7-day retention for anyone who needs one.

## Also in this release

- Membership Policy on the create form defaults to invite only and says what
  joining is, so it agrees with the Minimal template instead of contradicting
  it. Existing patches are untouched.
- Hovering a patch's card in the list dims the rest of the quilt, using the
  same dim a tile's own hover uses. Nothing happens when the tile is off
  screen.
- A claim leaves the "approved, awaiting setup" queue once setup is done,
  and a completed claim can no longer be swept into "expired".
- The suggested-tags queue renders when it is empty, with "Nothing waiting
  for review", instead of looking unbuilt.
- The quilt-order dropdown is readable in dark mode, and the app now declares
  `color-scheme`, so native widgets follow the theme.
- Go 1.26.6 rather than the 1.26.0 Dependabot proposed, which would have
  moved a patched toolchain onto one with eight open stdlib advisories. The
  Docker build image is `golang:1.26-alpine`. Library bumps: go-webauthn
  0.18.0, go-sqlite3 1.14.52, x/text 0.41.0, x/time 0.16.0, devalue 5.9.2.
- For contributors: new ADRs and migrations are named from the clock
  (`docs/adr/YYYY-MM-DD-slug.md`, `migrations/YYYYMMDDTHHMMSS_slug.sql`).
  Both number spaces are closed and a test refuses a new numbered file.
  Existing files keep their names.

## Upgrading

**Take a backup first, and tell your patch admins what the first section
says.** Then:

```sh
docker compose pull patchwork && docker compose up -d
```

Four migrations run. Two are purely additive: `20260918T145410_scoped_trust`
adds three tables and two defaulted columns on `nodes`, and
`20260918T185545_usage_counts` adds two tables. The other two rewrite values,
which is why `irreversible_migrations` is `true`:

- `075_follower_charters_off_by_default` sets `charters` to `false` inside
  every patch's `follower_permissions`. On first boot the server also rewrites
  each affected patch's `governance-rules.json` in its git repo and notifies
  that patch's admins; a second boot finds nothing to do.
- `20260918T173950_default_closed_member_list_and_governance_record` adds
  `public_governance_record` and sets `public_member_list` to `nobody` on
  every row.

Rolling back to v0.28.0 works in the sense that the older image reads this
database and ignores the column it does not know. What it does not do is put
back the values those two migrations overwrote: nothing records which
patches had `everyone` or `admins` before, so a rollback leaves every member
list closed. The backup is how you would know.

A seamrip archive that predates either setting imports with it closed. That
is deliberate: a pre-069 archive would otherwise restore every roster in it
to public and undo the retraction with a file. An archive that carries the
setting keeps the value it carries.

This release is marked **breaking** because three defaults flip in a way that
changes who can see something, on patches that already exist, and because an
API route is removed. An unattended updater should stop here and let a person
read the first section.
