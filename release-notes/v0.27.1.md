**Do not deploy v0.27.0. Deploy this instead.** v0.27.0 shipped an
unauthenticated git transport that hands out every members-only charter of any
patch whose slug you can guess. It is latent in a build that predates the
transport and live the moment such a build is replaced by v0.27.0 — so an
instance still on v0.26.x was never exposed, and upgrading to v0.27.0 is what
would have exposed it. That image is public and stays published; this release
is the one to pull.

Nothing here is a migration. v0.27.0's five migrations (069–073) still run if
you are coming from v0.26.x, and everything in v0.27.0's notes still applies —
including the succession check you should do before upgrading at all.

## A clone took the whole shelf

```sh
git clone https://<instance>/api/v1/nodes/<slug>/governance.git
```

That worked, signed in or not, for any active or unclaimed patch — private and
unlisted included. docs/adr/036 gives every governance doc its own visibility,
defaulting to `members`, and `ListGovernanceDocs` keeps that promise row by
row; the transport kept none of it. Both routes were mounted with no auth
middleware, CSRF exempts `/governance.git/`, and `handleInfoRefs` advertised
every ref without asking anything about the caller. `DirectEdit` mirrors a doc
into that repo on every content change regardless of its visibility, so the
repo held the members-only ones too.

**The bodies were not the whole of it.** Commits are authored
`DisplayName <username@patchwork.local>`, so a clone also named who edited what
and when — the question docs/adr/006's per-membership visibility switch exists
to answer.

The transport is now gated on the whole-shelf rule rather than the
per-document one: `GitHTTPHandler` takes an authorizer instead of a resolver,
and asks `canReadPatchDocs` — the same function that decides whether a viewer
is handed the members-only shelf over REST. One rule, stated once, asked at
both doors. There is no half-clone, so there is no caller who may be handed
half of one.

"No such patch" and "not for you" are one answer: the same 404 with the same
body, because two answers are an oracle for the existence of a private patch.
**Anonymous clone is gone on purpose** — nothing in the tree consumed it, no
UI advertises a clone URL, and a public charter is already readable over REST
and ActivityPub. What anonymous clone added was the history and the
authorship. See docs/adr/110.

Found in an outside source-level review and confirmed against a running
instance before the fix was written.

## A public voter list named people who had hidden

`GET /api/v1/proposals/{id}` is a public read and never consulted the
per-membership visibility switch, so it returned every voter's username,
display name and user id to anyone, signed in or not. Only members vote, so
each of those rows published the exact fact the switch had taken down — and it
is worse in aggregate than per row, because across a patch's proposals the
voter lists reassemble the member list.

Names are now **substituted rather than dropped** for a reader outside the
patch: `HiddenMemberName` beside `DeletedAccountName`, the same move for a
different reason, so the tally still adds up and the record still shows that
somebody voted. Inside the room — an active member or admin, or an instance
admin — nothing changes. A follower is outside it: a follower is an observer,
and the people in a patch are not theirs to enumerate.

Deliberately still named, because the act is the person's own public speech
rather than a byproduct of membership: a proposal's author, a comment's
author, a candidate standing for a seat.

## An event's permalink ignored the event's visibility

`GET /api/v1/events/{id}` checked whether a submission was still pending
review and nothing else. It never read the event's own `visibility`, so a
members-only event was fully readable by anyone holding the link — and the CSV
door accepts a visibility column, so there was a real path to a hidden event
that nothing hid.

It now applies the rule `ListEvents` and the ICS feed already apply: a member
or admin of the event's own patch, 404 to everyone else, and a confirmed link
from another patch never widens it. A private *patch* is unlisted rather than
locked, so its public events stay readable by anyone holding the link, exactly
as its page does — this gate reads the event's visibility and never the
patch's. The pending-submission branch still decides the whole question for a
submission, so a members-only event awaiting review does not vanish from the
queue that has to answer it.

## Upgrading

`docker compose pull && docker compose up -d`.

No migrations run in this release. If you are coming from v0.26.x, read
v0.27.0's notes first — its migrations and its succession check both still
apply, and you can go straight to 0.27.1 without stopping at 0.27.0.

Rolling back to v0.26.1 works and is the only rollback that closes the git
transport, since v0.27.0 is the release that opened it.

**What to do about what was already readable.** Only the first of these three
is new in v0.27.0; the other two have been readable for longer. Nothing in a
patch release can un-disclose what a public endpoint served, so if your
instance has patches whose charters or membership were meant to be private, it
is worth telling those patches what the exposure was rather than only closing
it. The audit log will not help here — none of these were writes.
