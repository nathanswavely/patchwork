Sixteen pull requests since v0.27.1, five decision records (ADRs 111–115), and
one migration. Nothing here changes a config key, a volume, or an endpoint an
existing client depends on.

## The quilt can be quieted

A reader said the quilt looks cluttered. It does, and the honest fix was not to
draw quieter tiles — a patch chose its fabrics — but to let the reader turn the
volume down on their own screen. The new **Display menu** replaces the old
Light/Dark button and carries the quilt's visual modes.

**Muted never adds a color a patch didn't choose.** One transform at one
chokepoint: hue is kept, lightness is normalized onto a ramp shared by every
tile, and chroma is only ever *capped*, never raised. A patch whose identity
color is achromatic draws a grey ramp because it genuinely chose to be
achromatic — no fallback, no special case, and in a field of muted color it
becomes the most distinctive tile on the quilt rather than the least. Six
fabrics in, six distinguishable fabrics out. See docs/adr/112.

Alongside it, hash-assigned appearance now draws from the whole hue wheel
instead of clustering in six reds, so patches that never picked a look are
told apart at a glance. Seeded listings no longer carry a pinned appearance at
all — they let the quilt decide.

## The reader can put the list away

The cards pane has been 45% of the window since it was drawn, and nobody chose
that for the reader. Now it is shown or hidden, and the reader says which:
shown is exactly what shipped before, hidden gives the canvas the whole window.

There are deliberately no widths in between. An earlier build of this had three
stops including a single-column pane, and using it settled the question against
itself — a narrower pane is a worse list and a barely better quilt. One bit.
See docs/adr/111.

## A patch may ask for a word

Tags stay instance-curated, but a patch admin can now **suggest** one. A
suggested tag is worn provisionally by the patch that proposed it and is
invisible to everyone else until an instance admin approves it; a declined word
keeps its row so the same suggestion does not come back every week. See
docs/adr/114.

This is the one migration in the release, and it is additive — see **Upgrading**
for the single thing worth checking first.

## Claiming a patch asks who can join

Claiming a listing used to hand you a patch that admitted anyone, chosen by
nobody. Every listing is written with a membership policy; it decides nothing
while the patch is a listing, because an unclaimed patch takes followers only —
and then a claim made it the live door.

Setup now asks, seeded from the governance template you pick and following it
until you answer for yourself. A claimant who picks Minimal gets the
invite-only patch that template's rules actually describe; previously the
listing's value overruled it. Listings are written `invite_only` so that an
unchosen value fails closed. See docs/adr/039.

Membership policy remains governance — it lives in the patch's rules file, and
`PATCH /api/v1/nodes/{slug}` still refuses the field. But **Patch Settings →
Info** now states the current policy and links to the rules editor, because an
admin looking in the obvious place and finding nothing reads it as "there is no
such setting."

Patch Settings also now says when you are viewing it as an admin of the *quilt*
rather than an admin of the *patch*. That is disclosure only and grants nothing;
docs/adr/115 records the larger question of what instance-admin reach should be,
and deliberately defers changing it.

## Federation: a signature says what it covers

An inbound HTTP Signature carries its own list of which headers it signed, and
the verifier trusted that list — falling back to `date` alone when it was
absent, as the draft spec says to. So the *sender* chose how much of the request
its signature stood behind, while three checks downstream were resting on values
nobody had signed: the replay window enforced against a `Date` the replayer
writes, a body left unauthenticated when `Digest` is simply omitted, and a POST
captured for one inbox replayable into another.

**This was not exploitable as it stood.** The compensating checks are real and
every implementation Patchwork talks to signs the full set. The defect is that
the guarantees came from the sender's good manners rather than from the
verifier — the kind of thing that survives a refactor as a hole.

The verifier now names the floor it requires — `(request-target)`, `host`,
`date`, plus `digest` on methods that carry a body — and refuses a signature
covering less. A sender that covers more is accepted unchanged.

**One interop note.** Patchwork signs exactly this set, and so do Mastodon and
the other mainstream implementations, so quilt-to-quilt and Mastodon delivery
are unaffected. But the spec's `date`-only default is now refused. If you
federate with something unusual and inbound delivery stops, the log names the
header its signature failed to cover. That is a deliberate refusal, not a bug.
See docs/adr/113.

## Upgrading

```sh
docker compose pull patchwork && docker compose up -d
```

**One thing to check first.** Migration 074 adds a case-insensitive unique index
on `tags(name)`. SQLite's default collation is binary, so `Music` and `music`
have always been two separate rows, and the index **fails loudly** on a database
that holds such a pair — which means the server will not start. Only tags
created through the API could have collided; the admin page always lowercased.
Check before you upgrade:

```sql
SELECT lower(name), count(*) FROM tags GROUP BY lower(name) HAVING count(*) > 1;
```

Any rows returned must be merged by hand first. No rows, and the migration is
purely additive.

The rest of 074 adds columns with safe defaults and an index. Pre-existing tags
and seamrip archives written before this migration land as ordinary approved
vocabulary.

Rolling back to v0.27.1 works against a 074 database: migrations only ever apply
forward, nothing in this release drops or rewrites anything, and no query names
the new columns with `SELECT *`. Take a backup anyway — it is one command and
this is the first release carrying a migration since v0.27.0.
