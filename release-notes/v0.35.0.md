Nine pull requests since v0.34.0, two decision records (one accepted, one
proposed), and one migration (an added column). No config, volume, port
or Caddy changes, so this update is the image pull alone.

## The activity feed stops showing followers closed governance

The activity feed built its proposal and charter items from every patch a
person had a relationship with, follows included, and checked nothing
else. Following is free and needs nobody's approval, so any signed-in
account could follow an invite-only patch and see the **titles** of its
closed-record proposals and members-only charters in their feed. Event
items were already gated correctly.

Each item now asks the same question the patch's own pages ask: a proposal
shows only where the governance record is open or the viewer is an active
admin or member, and a charter only where it is public, the viewer is an
admin or member, or the patch grants its followers charters (#411).

The feed's event links are now `/events/{id}`, the route the app and other
clients know, rather than a patch-scoped path the web app only redirected.
A charter is dated by when it was created, so an edit no longer pushes an
old charter back to the top as if it were new (#412).

## Long lists read past their first page

Every list endpoint returns 20 rows unless asked for more, and a number of
screens read that one page as the whole list.

- **My Quilt cards** for a person with more than 20 relationships showed
  **Follow** on the patches they already followed. Each patch on the quilt
  and the map now carries the viewer's own standing, so a card no longer
  depends on a separate list loading in full (#465).
- **A patch's Events tab is a month view** with previous and next. It
  showed a patch's 20 oldest events; on lancasterpatchwork.org that was 20
  of 264 (#466).
- **Searching inside a patch, and the admin finder, ask the server**, so a
  search finds rows past the first page: events, proposals, members,
  reports and submissions. Matching folds case for plain ASCII letters
  only, so "tornado" no longer finds "Tornādo" as the old in-browser
  filter did (#466).
- **Patch Settings → Members, the admin submissions, claims and
  archived-patch queues, the noticeboard report queue, the successor and
  nominee pickers, and the event form's patch picker** all read every page,
  and the proposal list gains Load more (#465, #466, #414).
- A test now lists every paged route and fails when a screen reads one
  without following its cursor (#466).

## Governance on the web

- **Version history shows a side-by-side diff** again, and the compare
  view labels each side by version number (#414).
- **An approved request is credited to the maintainer who approved it**,
  not shown as "Applied by" its author.
- **The rules editor says where a change goes**: to the maintainer on an
  admin-decides patch, and on a patch that decides elsewhere it says why a
  member cannot propose one.
- **The proposal form follows the patch's venue and window**: "Open for
  discussion" with no voting window where decisions happen elsewhere, and
  the patch's own default window in place of a fixed 72 hours.
- **The document door says Edit** where an admin's edit applies directly.

## Your quilt's links can open in a listed iPhone app

An Apple app the quilt already vouches for (Administration → Settings →
Apps) now has a switch: **Open this quilt's links in the app**. Off by
default for every app, including ones already listed. Turned on, the Apple
association file gains an `applinks` block naming only that app, and
iPhones with it installed open the quilt's patch, event, people and
governance links in the app instead of Safari. Settings, sign-in links,
the admin panel, and every page that writes something stay in the browser.
The switch is admin-only and audited, with no step-up, since it routes
links to an app that already holds the quilt's passkeys. Apple can take up
to a day to notice a change. Android is unchanged. Decision:
`docs/adr/2026-10-18-a-listed-app-may-open-the-quilts-links.md` (#417).

## For client developers

- `viewer_standing` on `GET /api/v1/nodes/tree` and `GET /api/v1/nodes`
  items for a signed-in caller: `admin`, `member`, `follower`, `pending` or
  `invited`, omitted otherwise (#465).
- `role` on `GET /api/v1/me/nodes`, a comma list of `admin`, `member` and
  `follower`; an unknown role is a 400 (#465).

  `/nodes/{slug}/members`, `/admin/reports` and `/admin/submissions`, and
  `node_id` on `GET /api/v1/admin/claims` (#466).

## Upgrading

**Take a backup first**, then:

```sh
docker compose pull patchwork && docker compose up -d
```

One migration runs: an `open_links` column on `native_apps`, defaulting to
off, so no instance's published files change until an admin turns the
switch on.

No `git pull` is needed; nothing outside the image changed.

**Rolling back to v0.34.0 is not clean.** The migration is additive, but
the older binary refuses to start against a database whose
`schema_migrations` names a migration it does not know. To go back,
restore the backup taken above rather than starting the older image
against this database.
